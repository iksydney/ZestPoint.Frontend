# ZestPoint Frontend: Architecture

> Repo: `ZestPointDashboard/ZestPoint.Frontend/` (Angular 18). Last reviewed: 2026-10-14 (after Phases 1-7 of `Firstprompt.md` and the POS/Stock/Purchasing navigation of `POSContinuum.md`, section 12).
> Sister repos: **Backend** `../../ZestPoint/architecture.md`, **Mobile** `../../ZestPointMobile/architecture.md`.
> Shared rules live in `constitution.md`; defects and gaps are logged in `../../findings.md`. Delivery summary and run instructions: `../../ZestPoint/DELIVERY.md`.

## 1. Purpose

One Angular single-page app, one origin, one port (`ng serve` -> `:4200`) containing:

1. the **public marketing site** (`/`, `/features`, `/pricing`, `/contact`, `/privacy`, `/terms`) for hospitality **and retail**; its forms post to the real API;
2. **registration, sign-in and onboarding** (`/register`, `/login`, `/accept-invite`, `/onboarding`). Registration step 1 picks the main business type plus optional extra types; step 2 picks the default currency and which extra wallets (USD, CNY, JPY, NGN; `WALLET_CURRENCIES` mirrors the API) to open. Continue / Create stay disabled until the step is valid, but never silently: each field shows its own message under it once visited, and a "Still needed: ..." / "Waiting for the address availability check" status beside the button names what is missing or pending (local checks are UX only; the server re-validates on register and its field errors replace the local ones). `/register` and `/accept-invite` have no venue theme yet, so they follow the public light/dark choice (OS setting until the visitor picks, shared with the marketing site, Sun/Moon switch in the header; `PublicThemeService.attach(true)` adds `zp-entry` to `<html>` and `styles.scss` swaps the colour tokens for an AA-checked light set); sign-in stays venue-driven (FND-075). `/accept-invite` asks for the default PIN from the invitation e-mail once, then a new PIN;
3. the **signed-in application** under `/app` (dashboard, POS, inventory, catalogue, staff and roles, branding, branches, operations settings, subscription), gated by authentication, screen-level RBAC, the workspace lock and module entitlements;
4. the **platform operator interface** under `/platform` (a separate sign-in: overview, companies, plans).

The browser only shapes the experience. **Every rule is enforced again by the API**; hiding a button or redirecting a route is a convenience, never a control.

## 2. Stack

Angular 18 (standalone components, signals, new control flow, `OnPush`), TypeScript strict + `strictTemplates`, Tailwind CSS 3 with CSS-variable tokens, RxJS for HTTP only, **Dexie (IndexedDB)** for the offline queue, **@microsoft/signalr** for the live bar-order notices (section 12), `lucide-angular` icons, Playwright for end-to-end tests. No unit-test runner is configured (see FND-037).

## 4. Routing and guard order

`/app` runs `authGuard` (restores the session from the refresh cookie first) then `workspaceLockGuard` (restricted company: only the subscription screen, or `/restricted` for staff without `subscriptions.view`). Each screen then runs `screenRbacGuard` (permission) and `subscriptionGateGuard` (module `locked` -> `/upgrade?feature=...`, which names the module and says who can change it; and, when the route carries `data.screen`, a screen the organisation was not given -> `/upgrade?feature=...&screen=...`, which names that screen). `/app` itself redirects to the first screen the person may use. `/platform/**` needs an operator session: the access token is held in memory only, and `platformGuard` / `platformPermissionGuard` first `await PlatformAuthService.ready()`, the one attempt to restore it from the httpOnly `zp_prt` cookie (`POST /api/v1/platform/auth/refresh` with `X-Requested-With: ZestPoint`), so a reload, a new tab or a browser restart keeps the operator signed in and only a failed restore reaches `/platform/login` (which itself forwards an already-signed-in operator to the overview). The interceptor attaches the operator token to `/api/v1/platform/*` only; on a 401 it makes ONE refresh attempt and replays the request, else signs the operator out. Signing out revokes the server session, removes the cookie and tells the other tabs of the browser (BroadcastChannel) to return to the sign-in; a tab that is not told (no BroadcastChannel) loses the session when its 60-minute token runs out.

## 5. Session, RBAC and entitlements

`AuthService` keeps the access token and the session snapshot in signals (never web storage); the refresh token is an httpOnly cookie, so a reload calls `restore()`. A network failure during refresh does **not** sign the person out (the POS keeps working offline). The snapshot (permissions, branch ids, per-module access, subscription state with the account banner) is **UX only**; `auth.reload()` refreshes it after any billing action. Permission and module keys live in `rbac.model.ts` and are checked against the backend by a contract-parity test.

**Below the module: screens and buttons (2026-11-12).** The session's `subscription.access` lists what the organisation was **not** given (default is allowed): `deniedScreens` (menu keys = `APP_NAV` keys), `deniedActions` (permission codes) and `byBranch` (only what differs for a branch). `AccessService` turns it into `screenAllowed(key)`, `actionAllowed(code)` and `canShow(nav)` (module not locked AND screen not withheld, read by the shell menu, the dashboard tiles and the landing guard) and adjusts it for the branch picked in the header. **Withheld screens are hidden** from the menu and a direct URL shows the "Not included in your plan" page; **withheld buttons stay visible but unavailable**: the `zpAction="<permission code>"` directive disables the host, exposes the reason as `title` and `aria-disabled`, and stops the click in the capture phase (a template's own `[disabled]` outranks a directive host binding). `zpAction` is UX only and does not look at the role (that stays `hasPermission`). Coverage is staged and listed in `../findings.md`; any button not yet migrated still fails with the server's `not_entitled` message and the app then re-reads the snapshot (`AccessService.noteRefusal`, throttled to once per 10 s). The server remains the authority.

The **account banner** (`zp-account-banner`) shows on every signed-in screen: what is wrong or coming, the affected modules, the reason and the next step ("Update payment", "Choose a plan"), in fixed system colours that are never themed. People who cannot manage billing see the message and who to ask.

## 6. Theming

The saved company theme is applied as CSS variables (`--primary-rgb`, ...) by `ThemeService` and used by every screen through Tailwind tokens (`bg-primary`, `text-ink`, ...). The branding editor previews a **draft** by scoping the same variables onto the preview frame (`themeVariables()` is the one function for both), so unsaved colours never leak to other sessions. System alerts (`.sys-alert`) and the marketing site (`.zp-public`) are deliberately outside the tenant theme.

## 7. Offline-first POS (Phase 5)

`PosStore` applies every sale-floor change to the bill on screen immediately and appends a matching operation to the Dexie queue; `SyncAgentService` replays the queue through `POST /api/v1/sync` (in order, idempotent by client operation id) when online, on reconnect and every 15 s, and the server's figures then replace the local ones.

- Queue rows are tied to the **tenant and the signed-in member**; only that member's operations are ever sent (the server authorises them as the sender). A rejected operation stays visible under "not accepted" with the server's reason and is never silently dropped.
- Works offline: open a bill, add/change/remove items, send, discount, tip, take **cash**, request a void, stock adjustments and scale/manual measurements (into an audit that already exists on the server). Needs the server (and says so): card/transfer payments, split, merge, move table, refunds, receipts, starting an audit, purchasing.
- The catalogue, tax settings and branches are cached for offline use. A reload while offline needs a prior online session (FND-025).
- Scale audits: `ScaleService` offers the Bluetooth adapter (standard Weight Scale service only), a clearly labelled **demonstration** scale, or typed entry (`Manual`). Readings are recorded with their true source; a weight becomes millilitres only if the item has a density.

## 8. Subscription and platform screens

`/app/subscription` shows plan and status, the renewal/grace dates in the company time zone, usage against limits, per-module access with upgrade hints, plan comparison and change, payment method (development tokens are explained on screen), pay now, cancel/resume, billing history and the entitlement ledger. `/platform/*` lets an operator find companies, see their subscription, ledger and usage, act on them (every action needs a written reason) and edit plans. **Access** (company detail, `zp-access-tree`): the company's Module > Screen > Action tree with where each answer comes from (plan, operator, default, module off), allow/withhold per item (optionally one branch and an end date), **Grant whole module / Revert to plan**, **Grant whole application** (required end date, at most 90 days, unbuilt modules skipped) and **Revert**; the screens, buttons and modules come from the server's catalog (`GET /platform/access/catalog`) so a new screen appears without a change here. The Companies list selects several companies for **bulk apply** (per-company results, one idempotency key per dialog), the overview lists **grants ending in 7 days**, and the plan editor sets item rules and "selective" modules with the same catalog. Operators without the billing right see the tree read-only.

## 9. Testing

`npx playwright test` drives the real stack: the API on `:5250` against the throw-away PostgreSQL database `zestpoint_e2e` (created by the API's startup migrations on the first run; never part of any deployment, drop it any time) and `ng serve --configuration e2e` on `:4300` through `proxy.e2e.conf.json` (the `e2e` configuration swaps in `environment.e2e.ts`, so your own `.env.*` files are never touched). Suites: registration/branding, staff/RBAC, POS and inventory (including offline), subscription and platform, access control (`access-control.spec.ts`: withhold a screen and a button, one-click module and application grants and reverts, bulk apply, read-only operator, phone width and dark theme), operator sessions (`platform-session.spec.ts`: a reload or a new tab keeps the operator signed in, sign-out reaches every tab, the refresh cookie is httpOnly), dashboard and receipts, public forms. Edge is the only browser. The server and credentials come from `ZESTPOINT_E2E_PG` (its database must end in `_e2e`) or, if that is unset, from the backend's `appsettings.Development.json` with the database name forced to `zestpoint_e2e`, so the suite can never write to the dev or prod database (rules and tests in `e2e/e2e-database.ts`). The API runs from the sibling `ZestPoint/ZestPoint/ZestPoint.API.csproj`; set `ZESTPOINT_E2E_API_PROJECT` to a scratch copy when Visual Studio keeps the real one's DLLs locked. Before the first e2e run on a database with many old companies, start the API once (the subscription backfill can take a minute).

## 10. Environment

`npm start` runs `scripts/generate-env.mjs` to write `src/environments/environment.ts` from `.env.development` (API base URL, site URL); production builds read `.env.production`. Nothing secret belongs in either file.

## 12. Navigation groups, report screens and stock screens

- **One list** (`core/navigation/app-nav.ts`): every screen has a stable `key`, label, route, icon, permission(s), module, group (`pos`, `stock`, `purchasing`), optional legacy `shortcut`, `needsBranch`, `quickAccess` and a lazy `load`. `app.routes.ts` builds the route table from the entries that have `load` (guards: `screenRbacGuard`, then `subscriptionGateGuard`), the sidebar and landing guard filter the same list by permission and module, the shell derives breadcrumbs from it, and the dashboard shows the `quickAccess` entries. Screens keep their original hand-written routes (dashboard, inventory console, catalogue, subscription, staff, settings). Authorisation never reads a label or a shortcut.
- **Menu** (`shared/ui/nav-sidebar.component.ts`): expandable groups (the group holding the current screen is always open), active-route highlight, search, arrow/Home/End keys, legacy keys that fire **only while focus is on an entry inside that group's list**, tooltips, an off-canvas drawer on phones. Locked modules and refused screens are not shown; typed URLs are refused by the guards and the API.
- **Report screens** (`features/reports/`): `ReportViewComponent` renders any report from its `ReportDefinition`: only the filters that report supports, server sorting and paging, summary figures, applied-filter chips, generated-at and currency, column visibility, loading/empty/error states, calculation notes, CSV export (shown only with `reports.export`), print, and filters kept in the URL (refresh/back/drill-down keep them). It never calculates a figure. Row actions come from a template the host supplies (serial numbers) and the re-order report offers selection to create purchase-order **drafts** (grouped by supplier and branch; nothing is sent or approved).
- **Workflow screens**: Start / End of Day (`pos-billing/day-management`), Add / Modify Stock, Stock Groups, Global Maintenance (preview then apply), Adjustments (request/approve/reject/cancel, reasons), Stock Take (counts, blind mode, review, reconcile; plus the variance report tab), Labels (Code 128 / EAN-13 drawn from `core/barcode.ts`; the screen only opens the browser print dialog and says it cannot know whether anything printed), Serial Numbers, Purchasing orders (reuses the existing tab), Suppliers, Supplier Payments. Mutating calls carry client-generated idempotency keys; every screen shows read-only mode and server errors.
- **Contract**: `core/models/nav-ops.model.ts` and `ops.model.ts` mirror the backend DTOs; `rbac.model.ts` mirrors the permission keys (parity-tested). Cost fields arrive as `null` for roles that may not see them and the screens hide those columns.
- **Tests**: `e2e/navigation.spec.ts` (10 tests: menu structure and order, all 43 entries opening, shortcuts and arrow keys, menu search, cashier denial and typed URLs, shift and supervisor review, groups/items/adjustments/stock take/labels, reports with filters/export/print, purchasing, phone drawer). Existing specs were updated for the new "Point of Sale" menu entry.
- **Offline shifts and serials**: `core/services/shift-store.service.ts` (`ShiftStore`) is online-first and falls back to the durable sync queue (`shift.*` kinds) with the shift cached in Dexie; Start / End of Day shows `day-offline` and says expected cash is recalculated on sync. The till asks for a serial on products with `tracksSerials`, and the goods-receipt dialog takes serial numbers, supplier and purchase tax. The re-order screen sends one purchase-order idempotency key per supplier/branch group.
- **Tills and staff codes** (2026-11-13): Start / End of Day has no terminal field. The server gives the cashier the lowest free `Till N` at the branch and the screen shows it (`day-till`) once the shift is open; a shift started offline shows "Till number comes when this device syncs" until the queued `shift.open` is applied. `OpenShiftRequest` no longer has `terminalId`. A staff code is a string such as `BHL-007` (`staffCode: string` in `api.model.ts`, `staff.model.ts`, `support.model.ts`); the sign-in field accepts letters and digits in any case with or without the dash (`STAFF_CODE_RE` in `features/system/login.component.ts`, mirroring the server). Right after a staff member is added, `staff-list.component.ts` opens a "Staff member added" panel (`staff-added`, code in `staff-added-code`) with the code, the venue and the sign-in steps; the invite path with a development link keeps opening the detail dialog, which also shows the code.

- **Support and the operator console**: company screen `features/support/support.component.ts` (`/app/support`, permission `support.view`/`support.create`, kept reachable while the workspace is locked). Platform screens under `features/platform/`: `platform-support` (queue and summary), `platform-ticket` (thread, internal notes, assignment, status, priority), `platform-customers` and `platform-customer` (CRM), `platform-users` (people care with a mandatory reason), `platform-operators` (Admin). `PlatformAuthService.can()` reads the permission list returned at sign-in to decide what the console shows; `platformPermissionGuard` turns back typed addresses; the server re-checks everything. Models in `core/models/support.model.ts`, calls in `core/services/support.services.ts`. e2e: `e2e/support-portal.spec.ts` (3 tests).


- **Purchase order workstation and receiving**: `features/purchasing/purchase-order-workstation.component.ts` (`/app/purchasing/orders/:id`, `new` starts a document; one route serves new and saved so the screen is not rebuilt mid-save), `goods-receiving.component.ts` (`/app/purchasing/orders/:id/receive`), `goods-receipt-view.component.ts` (GRN, second key, claim slip), `receiving-queue.component.ts`, `purchase-orders-page.component.ts` (document list), `supplier-dialogs.component.ts` (find or add a supplier without leaving the order), `features/inventory/bins.component.ts`. Arithmetic lives in `core/purchase-math.ts` (same worked examples as the server). Typography is Syne / Plus Jakarta Sans / JetBrains Mono (`font-syne`, `font-jakarta`, `font-data`); every colour is a venue theme token. Icons are inline SVG (`shared/ui/icon-paths.ts`, `zp-icon`), so nothing needs the network. Effects that write signals must pass `allowSignalWrites`; `track` expressions must not use `??` (Angular generates an undefined temporary).

- **Bar man method** (2026-11-13; backend section 17). Registration step 1 asks a bar-type business "Will you use the bar man method?" (`bar-man-question`, required Yes/No; types in `BAR_MAN_METHOD_TYPES`, mirroring the API) and sends `useBarManMethod`; Operations settings shows the switch (`bar-man-section`) only to such a business. `core/services/bar.services.ts` holds three things: `BarOrdersApi` (the calls), `FloorLiveService` (one SignalR connection to `/api/v1/hubs/floor`, token from memory via `accessTokenFactory`, automatic reconnect for as long as the person is signed in, stopped at sign-out) and `BarStore` (whether the company uses the method, the bar's queue, the orders this person sent, which ones just arrived or need attention, a 30-second clock for "4 min ago"). The hub only says "bar order X changed"; the store then re-reads through the API, so everything on screen passed the usual tenant, branch and permission checks, and a reconnect simply re-reads. A new order or a "ready" pops up and plays a short two-note sound made in the browser (no audio file; can be muted; the first read after sign-in is silent). `features/pos-billing/bar-dock.component.ts` (`zp-bar-dock`, mounted in the shell) is the floating button with a count, the prompts and the expanding panel; `bar-order-card.component.ts` is one order for either side (bar man: take, can't make with a reason, ready, hand back; attendant: where it is, Collected / OK seen); `bar-orders.component.ts` is the Bar Orders screen (`/app/pos/bar-orders`, key `pos.bar`, permission `pos.bar_order.fulfil`): the live queue and the last 24 hours with how long each step took. The menu entry is offered only while the company uses the method (the shell filters it); the dock is rendered only for a person who takes part (bar permission, or `pos.order.edit` as an attendant) and never in a locked workspace. On the till each sent line shows where it is (`bar-state-*`: waiting at the bar, being prepared, ready to collect, served, bar can't make this) and the open bill re-reads itself when the bar changes it (a bill with unsynced edits keeps its local figures). The dev and e2e proxies forward WebSockets (`"ws": true`). e2e: `e2e/bar-man.spec.ts` (4 tests, three browser contexts: the question at registration; attendant to bar man and back live with stock checked before and after dispatch, plus phone width and dark mode; can't make; off by default, switched on in settings, a waiter cannot open the bar's screen, a supermarket is never offered it).

- **Voids need an authoriser** (2026-11-13; backend section 18). The till's void dialog (`void-dialog`) asks for the reason and then for the authoriser through `features/pos-billing/void-authoriser.component.ts` (`zp-void-authoriser`: Staff code and PIN, or Email and password). The button stays off until a pair is typed; a refusal keeps the dialog open with the server's message and wipes the PIN or password box. The component exists only while the dialog is open, and its fields are marked (`autocomplete="one-time-code"`, non-credential names) so a browser's password manager does not fill the signed-in person's saved sign-in. `PosStore.voidWithAuthoriser` calls the server directly (never the offline queue; the dialog says so when offline). "Void whole bill" (`void-bill`) uses the same dialog. Requests left from the old flow appear as "Old void requests" only while any exist; approving or rejecting one asks for the same details. New report screen Void History (`/app/pos/reports/void-history`, key `pos.report.voids`, permission `pos.void.approve`). The Add staff and Set PIN fields carry the same marking (the browser was filling the owner's own e-mail and password into a new staff member's name and PIN). e2e: `pos-inventory.spec.ts` "a cashier cannot void alone".

- **Stock card** (2026-11-13; backend section 19). `features/inventory/stock-card.component.ts` (`zp-stock-card`) is the one card to add or change a stock item, laid out after the legacy Stock Card: identity and sale rules on top, a price grid (Retail, Trade, Wholesale, Reseller, Bundle, On special, Minimum) with one two-way Markup % row on Last Cost, the special's period in the **company's** time zone (`core/time-zone.ts` converts to and from UTC), points, tax, account codes, levels, units and bin on the left, costs and live figures on the right, and tabs for other part numbers, the picture (fetched as a blob because it needs the session) and links to the item's history, sales and receipts. Parts not built yet are shown as "Not tracked yet" or greyed out, and stored-only settings say "(stored)". Add / Modify Stock opens it for New and Edit (`?edit=<id>` or `?edit=new`), with Previous / Next over the list on screen; **Add SKU on the purchase order** (`po-add-sku`) opens it for a new item pre-filled from the scan box (digits become the barcode, anything else the name) and puts the saved item on the document; pressing Enter in the scan box still looks up an existing item. "Delete" is Deactivate: items are never physically deleted. The till shows `special price`, `no tax` and `no discount` on bill lines and has no quantity buttons for an item sold one per line; `order-calc.ts` mirrors the server's tax and whole-bill discount rule. The catalogue editor edits `regularPrice`, never the special in force. e2e: `e2e/stock-card.spec.ts` (3 tests).
- **Selling units** (2026-11-13; backend section 20). The stock card's **Unit of measure** tab (`sc-tab-units`, needs a saved item) lists, adds and removes the item's selling units through `InventoryApi.units / saveUnit / removeUnit`; it shows what each sells for now (price x size) to people who may see prices. At the till, picking a product that has units opens the `unit` dialog (Single, then each unit with its price) before modifiers; scanning a unit's barcode sells that unit without asking. `PosStore.addProduct(..., unit)` names the line `Name (Unit of N)`, prices it `round2(price * size)` and queues `sellingUnitId`; the server recomputes both. e2e: `e2e/stock-card.spec.ts` (4 tests).
